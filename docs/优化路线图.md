## 执行约定

1. **阶段制交付**：每阶段完成 → 本地提交（不推送）→ 交你验收 → 你确认后我才开始下一阶段。
2. **阶段内自洽**：每阶段结束时代码可独立工作，`npm run verify` 必须 11 道闸门全绿；不做半成品。
3. **全局硬约束**（不可协商，任何阶段都适用）：
   - `src/core/` 14 个文件冻结（SHA-256 基线），不得修改；
   - 不新增生产依赖（只允许 `react` / `react-dom`）；
   - 不放宽任何既有断言；
   - 不改变金额与结算结果。
4. **每阶段交付物**：改动说明 + 验证证据（闸门输出、实测数据）+ 一份「需要你亲手点一下确认」的检查清单。

## 阶段总览

| 阶段 | 主题 | 覆盖审计项 | 风险 | 粗估 |
|---|---|---|---|---|
| 一 | 小修与真 bug | P2-6、P1-5、P1-6、无障碍 3 项 | 低 | 1–1.5 h |
| 二 | 节奏档位与跳过等待 | P1-1 | 中（连动 G11 / E2E 时序假设） | 2–3 h |

> 顺序理由：先修「用户能立刻看见的错」，再做「用户能感知但会动时序假设」的，再做「新功能」，最后做「大重构」——重构放最后，是因为前面几批改动会让重构目标（哪些代码真死了、哪些内联样式真重复）更清楚。

## 阶段一：小修与真 bug（低风险，快速见效）

**目标**：修掉一个真 bug、补上三个「用户困惑点」和三个无障碍缺口。全部是小改动，不改架构、不动时序。

### 任务

| # | 任务 | 涉及文件 | 说明 |
|---|---|---|---|
| 1.1 | 修 StatsPanel 盈亏颜色硬编码 | `src/ui/panels/StatsPanel.tsx`、`src/ui/App.tsx`、新增 `src/ui/format.ts` | 现状 `bankroll >= 1000 ? 'pos' : 'neg'`，1000 是默认起始筹码的字面量。用户把起始筹码改成 2000 后，资金 1500 会被判成「亏损红」；改成 500 后，资金 600 会被判成「盈利绿」。改为与 `settings.startingStack` 比较，并抽出纯函数 `netClass(bankroll, startingStack)` 便于单测 |
| 1.2 | 设置项标注「下一手生效」 | `src/ui/panels/SettingsPanel.tsx` | 6→9 人、盲注、起始筹码、AI 难度都是下一手生效，当前无任何提示。加一行说明 + 对「本手进行中」的项加视觉提示 |
| 1.3 | 全下二次确认 | `src/ui/components/ActionBar.tsx` | 全下单击立即执行，手滑会毁掉一手复盘。改为第一次点击按钮变「确认全下？」（3 秒内再点生效，超时复位）。**弃牌不加确认**——弃牌是高频动作，加确认会严重拖慢节奏；折中方案见「风险」 |
| 1.4 | 无障碍三项 | `src/ui/components/ActionBar.tsx`、`src/ui/App.tsx` | ① 加注滑杆补 `aria-valuetext`（读屏念「加注到 50，约 5BB」而不是只念「50」）；② tab 栏补 `aria-controls` + 内容区 `role="tabpanel"`；③ 底池变化补 `aria-live="polite"`（仅在底池数字变化时播报，避免刷屏） |

### 验收标准

- **自动化**：`npm run verify` 11 道闸门全绿；新增单测覆盖 `netClass`（3 组边界：起始 1000/资金 1000、起始 2000/资金 1500、起始 500/资金 600）；新增 E2E 一条——注入 `{startingStack:2000, bankroll:1500}` 存档后断言统计面板资金为负色，注入 `{startingStack:500, bankroll:600}` 断言为正色。
- **你手动确认**：
  1. 统计面板资金颜色在「起始筹码改成 2000」后是否正确；
  2. 设置面板能否一眼看出「这些改动下一手才生效」；
  3. 点「全下」是否出现二次确认、3 秒后是否自动复位；
  4. 弃牌是否**仍然**一键执行（不应变慢）；
  5. 用键盘 Tab 走一遍操作条，读屏（或 DOM 检查）能否念出加注额度的语义。

### 风险与回退

- 全下二次确认若被判定「仍然太慢」，回退方案是改成「长按 400ms 确认」或仅当跟注额 > 50% 筹码时才确认。阶段内可调，不需重开阶段。
- 1.1 抽出纯函数后若发现 StatsPanel 还有别处用 1000 做判据，一并改（会在阶段交付里说明）。

## 阶段二：节奏档位与跳过等待（P1-1）

**目标**：把固定的 AI 思考时长变成可选的档位，并提供「跳过当前等待」，把练习吞吐还回来。

### ⚠️ 开工前需要你拍板的一个取舍

审计建议三档：拟真 1.1–2.4s / **快速 0.35–0.6s（设为默认）** / 瞬时 0。

但你此前明确要求过「AI 决策下限必须 > 1 秒，不允许 1 秒内出决策」。两者冲突。三种选择：

| 选项 | 含义 | 代价 |
|---|---|---|
| A（推荐） | 保留「拟真」为默认（下限 1.1s），快速/瞬时作为用户主动选择 | 默认体验不变，吞吐改善要靠用户自己去开；不算真正解决审计的 P1-1 |
| B | 按审计建议把「快速」设默认 | 与你的原始需求冲突；首次进入的用户会觉得 AI 变「秒出」，拟真感丢失 |
| C | 默认拟真，但在**设置面板**和**首屏**各放一个显眼的档位切换 | 折中，多两处 UI |

**我倾向 A 或 C**：需求变更应由用户主动选择，不该由我悄悄改默认值。请在阶段二开工前告诉我选哪个。

### 任务

| # | 任务 | 涉及文件 | 说明 |
|---|---|---|---|
| 2.1 | 持久化节奏档位 | `src/store/schema.ts` | **不能加到 `Settings`**——`Settings` 定义在 `src/core/types.ts`，属冻结区。改为在 `PersistedState` 增加可选字段 `pace?: 'realistic' \| 'fast' \| 'instant'`，读取时 `?? 'realistic'`（按上面选项调整默认）。**不递增 `SCHEMA_VERSION`**：新增可选字段 + 读时缺省，不构成破坏性变更，旧存档无需迁移 |
| 2.2 | 时长区间参数化 | `src/ui/thinkTiming.ts` | 新增 `AI_THINK_RANGES = { realistic: {minMs:1100, maxMs:1800}, fast: {minMs:350, maxMs:600}, instant: {minMs:0, maxMs:0} }`；`aiThinkDelayMs` 接受档位参数。保持「每个 ai-action 步只抽一次」的既有性质 |
| 2.3 | 设置面板加档位 | `src/ui/panels/SettingsPanel.tsx`、`src/ui/App.tsx`、`src/ui/controller.ts` | 三选一控件 + 说明「只影响等待时长，不改变 AI 决策」 |
| 2.4 | 长按 S 跳过当前等待 | `src/ui/App.tsx`、`src/ui/useTableShowcase.ts` | 按住 S 把当前 step 的剩余等待压到 0（只压缩等待，不跳过决策、不改变动作序列） |
| 2.5 | 适配时序假设 | `tests/e2e/ai-think-timing.spec.ts`、`scripts/dev-smoke.mjs`、G11 | 该用例现在断言「每次 ≥1000ms」，档位化后必须显式切到「拟真」档再断言，否则在快速/瞬时档下会假红 |

### 验收标准

- **自动化**：`npm run verify` 全绿；`think-timing.test.ts` 补三档区间断言 + 「档位只影响 delayMs，不影响决策序列」的回归（同一 seed 三档跑出的 `actions` 序列必须逐条相同）。
- **实测数据**（阶段交付里给表）：三档各自 20 次决策的实际耗时分布；单手墙钟对比（拟真 / 快速 / 瞬时）。
- **你手动确认**：
  1. 设置里切换三档，下一手起节奏是否明显变化；
  2. 拟真档是否仍每次 > 1 秒；
  3. 按住 S 是否能立刻结束当前等待（松开后恢复正常）；
  4. 切换档位后 AI 的动作是否与切换前同一局一致（不应因档位改变决策）。

### 风险与回退

- 最大风险是「瞬时档」让 E2E 与 G11 的采样假设失效。对策：所有时序断言都显式声明档位，不依赖默认值。
- 若长按 S 与既有快捷键（N 下一手、数字键下注）冲突，改用空格或可配置；会在交付里说明。

## 阶段三：手牌回放（P1-4）

**目标**：历史面板里任意一手可以回放，复用现有牌桌渲染，纯前端零新增数据。

### 任务

| # | 任务 | 涉及文件 | 说明 |
|---|---|---|---|
| 3.1 | 回放帧生成（纯函数） | 新增 `src/ui/replay.ts` | `buildReplayFrames(record: HandRecord): ReplayFrame[]`——用 `record.seed` 重建牌局，逐条 `applyAction` 重放出每个动作后的快照。纯函数、可单测、不碰 React |
| 3.2 | 回放态机 | 新增 `src/ui/useReplay.ts` | 帧游标 + 上一步/下一步/自动播放/退出；独立于 `useTableShowcase`，避免污染演出层 |
| 3.3 | 历史面板入口 | `src/ui/panels/HistoryPanel.tsx`、`src/ui/App.tsx` | 每手加「回放」按钮；回放态复用 `TableView` 渲染，顶部条显示「第 N 手回放 · 第 k/m 步」+ 退出 |
| 3.4 | 回归测试 | 新增 `tests/e2e/replay.spec.ts`、`tests/unit/replay.test.ts` | 单测：帧数 = actions 数 + 1、末帧 `finished` 且结果与 `record.results` 一致；E2E：打开一手历史 → 回放 → 步进到摊牌 → 退出后统计未变化 |

### 验收标准

- **自动化**：`verify` 全绿；单测覆盖「帧数与动作数一致」「末帧结算结果与历史记录一致」「重放不修改传入的 record」。
- **你手动确认**：
  1. 历史面板每手都有「回放」按钮；
  2. 回放能逐步看到每个动作、公共牌逐街翻开、最后摊牌；
  3. 退出回放后，资金/统计/历史条数**没有变化**（回放绝不能写库）。

### 风险与回退

- 回放要复用 `applyAction`（core 冻结，但可调用），若发现某些 `HandRecord` 缺字段导致重建失败，降级为「该手不可回放」并置灰按钮，而不是抛错白屏。
- 若回放态机与演出层耦合过深，回退为「静态逐帧查看」（不做自动播放）。
